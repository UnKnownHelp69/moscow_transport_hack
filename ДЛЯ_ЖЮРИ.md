# Инструкция по проверке

## 1. Состав

| пакет | что это |
|---|---|
| `tram_odometry` | решение: ROS 2 Humble, Python (`ament_python`) |
| `tram_vehicle_msgs` | сообщения `VelocitySensor` и `DriverControllerCommand` (пакет из датасета) |

- Зависимости - только стандартные пакеты Humble: `rclpy`, `nav_msgs`, `sensor_msgs`,
  `geometry_msgs`, `diagnostic_msgs`, `python3-numpy`. Интернет не нужен.
- Данные модели (маршруты, станции, модель тяги, масштабы колёс) лежат внутри пакета.
- Два режима работы:
  - **с коррекцией по GNSS** (по умолчанию): GNSS нужен для выставки в первые секунды, а если
    фиксы приходят и дальше, они мягко поправляют положение;
  - **без коррекции по GNSS** (`gnss_correction:=false`): после выставки только колёса,
    контроллер и карта.

  Скорость от GNSS не зависит в обоих режимах. Как работают режимы - `docs/МОДЕЛЬ.md` §6.

## 2. Сборка

`WS` - корень workspace с `check-code` (в Docker-контейнере `check-code` это `/workspace`).

```bash
WS=/workspace                                    # или путь к папке check-code
cd $WS/src
git clone https://github.com/UnKnownHelp69/moscow_transport_hack.git mos_trap
touch tram_vehicle_msgs/COLCON_IGNORE            # пакет tram_vehicle_msgs из check-code не собираем
rm mos_trap/tram_vehicle_msgs/COLCON_IGNORE      # собираем наш, с DriverControllerCommand
cd $WS && source /opt/ros/humble/setup.bash
colcon build && source install/setup.bash
```

- Итоговая структура: `$WS/src/{checker_ros, tram_vehicle_msgs, mos_trap}`.
- Узел использует позицию контроллера (`/vehicle/driver_position_cmd`, тип
  `DriverControllerCommand`), поэтому нужен наш пакет сообщений. `VelocitySensor` в нём тот же.
  Два пакета с одним именем ломают `colcon build` («Duplicate package names»), поэтому пакет
  из `check-code` исключается файлом `COLCON_IGNORE`.
- Без `check-code`: создать `~/ws/src`, склонировать туда репозиторий, удалить
  `mos_trap/tram_vehicle_msgs/COLCON_IGNORE`, выполнить `colcon build` в `~/ws`.

## 3. Проверка

Все команды - из `$WS` после `source install/setup.bash`. Проигрывание идёт в реальном времени:
bag `30618_88aea4d9` длится ~22 мин, с темпом 2 - ~11 мин.

### 3.1. Один bag

```bash
src/mos_trap/scripts/run_with_checker.sh bags/30618_88aea4d9 2      # bag, темп (по умолчанию 1)
GNSS_CORRECTION=false src/mos_trap/scripts/run_with_checker.sh bags/30618_88aea4d9 2   # без коррекции
```

Скрипт запускает наш узел и `metrics` из `check-code`, проигрывает bag и печатает итоговые
строки `Velocity metrics` и `Position metrics`. Логи - в `checker_out/`. Третий аргумент -
`vehicle_id`, по умолчанию префикс имени bag.

### 3.2. Папка с bag

```bash
src/mos_trap/scripts/run_all_bags.sh bags 2          # папка (каждый bag - своя папка с metadata.yaml), темп
```

Таблица по каждому bag и среднее; логи - в `checker_out/<bag>/`, таблица - в
`checker_out/summary.txt`. Режим без коррекции - так же, с `GNSS_CORRECTION=false` впереди.

Результат на `30618_88aea4d9`, темп 2:

```
bag                      pos_rmse_m    pos_max_m  vel_rmse_ms
30618_88aea4d9             1.158305    11.100372     0.048768
mean (1 bags)                 1.158       11.100        0.049
```

| режим | RMSE положения 3D | RMSE скорости |
|---|---|---|
| с коррекцией по GNSS (по умолчанию) | 1.1-1.2 м | 0.049 м/с |
| без коррекции по GNSS | 1.5-1.7 м | 0.049 м/с |

`pos_rmse_m`, `pos_max_m`, `vel_rmse_ms` - строки `distance` и `velocity` из итога `metrics`.
В строке `mean` RMSE усредняются по bag, максимум - наибольший. RMSE положения немного
меняется от прогона к прогону (указан диапазон): время доставки сообщений в ROS каждый раз
разное.

### 3.3. Вручную

```bash
# терминал 1: узел
source /opt/ros/humble/setup.bash && source install/setup.bash
ros2 launch tram_odometry tram_odometry.launch.py vehicle_id:=30618    # без коррекции: gnss_correction:=false
# терминал 2: bag
source /opt/ros/humble/setup.bash && source install/setup.bash
ros2 bag play bags/30618_88aea4d9 --rate 2
```

- `source install/setup.bash` нужен в **каждом** терминале. Без него `ros2 bag play` не найдёт
  тип `tram_vehicle_msgs` и пропустит топики тележек (`Ignoring a topic ... package
  'tram_vehicle_msgs' not found`).
- `vehicle_id` - префикс имени bag (`30618` или `30639`), задаёт масштаб колёс вагона. Без него
  масштаб 1.0: для 30618 разницы нет, для 30639 это +0.27 % к пути.
- Узел лучше запускать до bag: он ждёт первый валидный GNSS-фикс. Если запущен позже,
  выставится по первому полученному фиксу.
- Несколько bag подряд можно проигрывать в один узел: по скачку времени он понимает, что начался
  новый bag (`input time jumped ...: new bag, estimator reset`), и выставляется заново.
- Без launch-файла: `ros2 run tram_odometry tram_odometry_node --ros-args --params-file
  $(ros2 pkg prefix tram_odometry)/share/tram_odometry/config/params.yaml`.

## 4. Входы и выходы

| топик | тип | содержимое |
|---|---|---|
| вход `/vehicle/front_bogie_velocity`, `/vehicle/rear_bogie_velocity` | `tram_vehicle_msgs/VelocitySensor` | скорость тележки, км/ч |
| вход `/vehicle/driver_position_cmd` | `tram_vehicle_msgs/DriverControllerCommand` | позиция контроллера |
| вход `/sensing/gnss/{master,rover}/fix` | `sensor_msgs/NavSatFix` | выставка по первым 3 с; дальше - коррекция, если фиксы приходят |
| **выход `/result/velocity`** | `tram_vehicle_msgs/VelocitySensor` | продольная скорость, **м/с** |
| **выход `/result/position`** | `nav_msgs/Odometry` | `base_link` в MGRS 37U local (`x = UTM37N_E − 300000`, `y = UTM37N_N − 6100000`, `z` - уровень головки рельса); ориентация - курс пути; `twist.linear.x` - скорость; ковариации заполнены |
| выход `/result/diagnostics` | `diagnostic_msgs/DiagnosticArray` | 1 Гц: выставка, `s`, `σ_s`, проскальзывание, отвергнутые показания, коррекции, частота, задержка |

- Публикация на каждое входное сообщение, ~40 Гц. Штамп выхода равен `header.stamp` входа,
  который его породил. `frame_id`: `map` у положения, `base_link` у скорости.
- До первого валидного GNSS-фикса выхода нет. После выставки в логе узла:
  `alignment done (...); GNSS kept for gentle corrections` (с коррекцией) или
  `GNSS subscriptions closed` (без коррекции).
- QoS подписок best-effort, публикация reliable.

## 5. Логи, метрики, задержка

| что | где |
|---|---|
| лог узла (1 Гц): частота, задержка, `s`, `σ_s`, число коррекций | `out N Hz, latency mean X / max Y ms, s=…, sigma=…, corr=…, slip=…`; при запуске скриптом - `checker_out/node.log` |
| задержка вход → публикация | в логе узла и в `/result/diagnostics` (`latency_mean_ms`, `latency_max_ms`, `latency_p99_ms`) |
| частота выхода | `ros2 topic hz /result/position` (ожидаемо ~40 при `--rate 1`) |
| итоговые метрики | строки `Velocity metrics` / `Position metrics` в `checker_out/metrics.log` |
| наш монитор точности по GNSS | `ros2 launch ... eval:=true`: каждые 10 с RMSE, в конце `FINAL …` |

`ros2 topic hz` и `ros2 topic echo /result/diagnostics` запускайте в отдельном терминале (после
`source install/setup.bash`), пока идёт `ros2 bag play`. Если в логе узла есть
`running on wheel speeds only`, собран пакет сообщений без `DriverControllerCommand` - см. §2.

## 6. Офлайн-проверка без ROS

Нужны bag из ветки `data` (`scripts/fetch_data.sh`) и `pip install numpy pytest`.

```bash
python analysis/refdata.py                                 # кэш эталонов из bag (один раз)
python analysis/evaluate.py val                            # без коррекции по GNSS, docs/МЕТРИКИ.md §2
TRAM_EVAL_GNSS=burst python analysis/evaluate.py val       # с коррекцией (пачки GNSS)
python analysis/robustness.py                              # инъекция сбоев
python analysis/build_model.py                             # пересборка data/ из train и OSM, побайтно та же
python -m pytest -p no:launch_testing tram_odometry/test -q
```
