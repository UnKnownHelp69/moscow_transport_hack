# Математическая модель

Критерий: описание математической модели - уравнения, структура, входы и выходы, оценка
ускорения и переход к скорости. Допущения и параметры - [ДОПУЩЕНИЯ_И_ПАРАМЕТРЫ.md](%D0%94%D0%9E%D0%9F%D0%A3%D0%A9%D0%95%D0%9D%D0%98%D0%AF_%D0%98_%D0%9F%D0%90%D0%A0%D0%90%D0%9C%D0%95%D0%A2%D0%A0%D0%AB.md).

Решение оценивает продольную скорость `v` и положение `base_link` трамвая. Основной контур
работает только на скоростях двух тележек и позиции контроллера водителя. GNSS нужен для
начальной выставки (3 с после первого валидного фикса). Если фиксы приходят и дальше, они мягко
поправляют положение вдоль пути (§6.4); если нет - оценка идёт только по колёсам и модели.
Скорость от GNSS не зависит никогда.

Ядро - `tram_odometry/tram_odometry/estimator.py`, без зависимостей от ROS. ROS-узел
(`node.py`) только передаёт в него сообщения и публикует результат.

## Коротко

- **Скорость.** Каждые ~25 мс два шага. Сначала модель тяги по положению ручки контроллера
  предсказывает ускорение, и скорость сдвигается на него. Затем приходит показание колеса, и
  фильтр Калмана подтягивает прогноз к нему. В обычной езде итог почти равен колёсам. Если
  колёса врут (залипание, выброс, юз), скорость ведёт модель тяги.
- **Положение.** Трамвай не сходит с рельсов, поэтому положение - пройденный путь `s` вдоль
  карты: скорость × время. Ошибку пути сбрасывают остановки у станций: трамвай встаёт у
  платформы с точностью 10-20 см.

## 1. Структура

```
 front/rear_bogie_velocity ─┐
                            ├─► 1. входы ─► 2. фильтр скорости ─► 3. путь s вдоль карты ─► 4. s → (x, y, z, курс)
 driver_position_cmd ───────┘   км/ч→м/с,    модель тяги +          станции, очереди,          │
                                отсев        проверка тележек       масштаб пути               ├─► /result/velocity
 gnss master/rover (3 с) ──► 0. выставка: вариант маршрута и начальное s                     └─► /result/position
```

Трамвай не сходит с рельсов, а курса во входах нет: нет ни IMU, ни поперечной скорости.
Поэтому положение оценивается как одна координата - длина дуги `s` вдоль известного пути.
`(x, y, z)` и курс берутся из геометрии пути в точке `s`.

Входы и выходы:

| | переменная | источник |
|---|---|---|
| вход | `z_f`, `z_r` - скорости тележек, км/ч | `/vehicle/{front,rear}_bogie_velocity` |
| вход | `n ∈ [−15, 15]` - позиция контроллера (+ тяга, − тормоз) | `/vehicle/driver_position_cmd` |
| вход, только выставка | фиксы антенн master и rover | `/sensing/gnss/{master,rover}/fix` |
| состояние | `v`, `P` (скорость и её дисперсия); `s`, `σ_s` (путь и его σ); вариант маршрута; масштаб пути `k` | |
| выход | `v`, м/с | `/result/velocity` |
| выход | `x, y, z` `base_link` в MGRS 37U local, курс, `v`, ковариации | `/result/position` |

## 2. Входы

- Скорость тележки приходит в км/ч: `z = velocity / 3.6 · k_veh`. `k_veh` - масштаб колёс
  вагона (износ, диаметр), подобран офлайн по GNSS-скорости train-прогонов: 30618 → 1.0004,
  30639 → 1.0027. Это эквивалент эффективного радиуса колеса.
- Отбрасываются NaN, ±inf, значения < −5 и > 150 км/ч. Показание тележки старше 0.5 с не
  используется.
- Время - `header.stamp` входных сообщений, не часы компьютера. Каждый топик проверяется на
  монотонность штампа отдельно. Показание, опоздавшее относительно других топиков не больше чем
  на 0.5 с, принимается: в bag штампы разных топиков перемежаются на 0.1-0.3 с.

## 3. Модель тяги: от позиции контроллера к ускорению и скорости

Модель - таблица `a = f(n(t − τ), v)`:
- `τ = 0.3 с` - задержка отклика привода и тормозов;
- 31 позиция контроллера × 7 интервалов скорости (0-1-3-6-9-12-15-30 м/с).

Задержка найдена перебором по максимуму R². Каждая ячейка - медиана производной скорости
колёс на train-прогонах, без GNSS (`analysis/fit_traction.py`). Качество: R² = 0.855,
СКО остатка 0.21 м/с².

Что видно в таблице:
- **Тяга** (`n > 0`) растёт с позицией и падает с ростом скорости - зона постоянной мощности
  двигателя (`F·v ≈ const`). На `n = +12`: 0.89 м/с² при 3-6 м/с, 0.66 при 9-12 м/с,
  0.55 выше 12 м/с.
- **Торможение** (`n < 0`): от −0.2 м/с² на `n = −1` до −1.3…−1.6 м/с² на `n ≤ −10`.
- **Выбег** (`n = 0`): около −0.03 м/с², это сопротивление движению (качение, воздух, кривые).
- **Стоянка:** при `v < 0.05 м/с` и `n ≤ 0` ускорение равно 0.

Масса, радиус колеса и коэффициенты сопротивления в явном виде не нужны. Таблица напрямую
аппроксимирует `a = (F_тяги(n, v) − F_сопр(v)) / m_экв`. Радиус колеса учтён через `k_veh`,
а масса, загрузка и уклон - в среднем, через остаток модели.

Переход к скорости - интегрирование ускорения в прогнозе фильтра (§4):
`v(t + Δt) = v(t) + a · Δt`.

## 4. Фильтр скорости (Калман со схемой доверия тележкам)

**Прогноз** на каждое входное сообщение (~40 Гц):

```
v ← clip(v + a(n(t − τ), v) · Δt, 0, 30)        P ← P + σ_a² · Δt,  σ_a = 0.3 (м/с)/√с
```

**Обновление** по показанию тележки `z`, инновация `y = z − v`:

1. **Проскальзывание.** Ускорение колеса `a_w` считается на окне 0.3 с. Режим проскальзывания
   включается в двух случаях:
   - `|a_w| > 6 м/с²` (физически недостижимо; экстренное торможение до ~2.5 м/с² проходит);
   - при тяге `a_w > max(a, 0) + 1.5 м/с²` (буксование).

   В режиме скорость ведёт модель тяги. Выход - когда `|y| < 0.3 + 0.5·t_slip` или через 2 с.
2. **Тележки расходятся** больше чем на 0.5 м/с (отказ датчика, залипание, выброс).
   Используется тележка, которая ближе к прогнозу.
3. **Работает одна тележка.** Показание принимается при `|y| < max(0.7, 4·√(P + R))`.
   Если его отвергают дольше 2 с подряд, оно всё равно принимается, чтобы ошибка модели не
   стала вечной.
4. **Иначе** - обычное обновление: `K = P/(P + R)`, `v ← v + K·y`, `P ← (1 − K)·P`,
   `R = (0.05 м/с)²`.

Две согласные тележки считаются достоверными, даже если модель с ними не согласна. Иначе
реальное экстренное торможение при почти нейтральном контроллере принималось бы за юз.

## 5. Путь вдоль карты

**Интегрирование.** Между событиями `s ← s + k · v̄ · Δt`, где `v̄` - среднее скорости в начале
и конце интервала. Неопределённость растёт с пройденным путём: `σ_s² = σ_0² + (0.003 · d)²`.

**Поправка пути при обновлении скорости.** Путь с предыдущего принятого показания колёс `t_k`
был проинтегрирован по прогнозу `v_pred`. Если после обновления скорость `v_post` и считать,
что она менялась линейно, получается трапеция:

`Δs = 0.5 · (v_post − v_pred) · min(t − t_k, 0.2 с)`.

Поправка не зависит от сообщений контроллера, запросов выхода и порядка почти одновременных
показаний двух тележек.

**Контрольные точки («станции»).** Это не список остановок из расписания, а точки пути, где
трамвай в записях останавливается каждый раз в одном и том же месте. Как они найдены
(`analysis/stops_db.py`, только train):
- стоянка - обе тележки медленнее 0.3 км/ч дольше 5 с, её положение берётся по GNSS-эталону
  и переводится в путь `s` вдоль карты;
- стоянки из всех рейсов группируются по `s` отдельно для каждого направления (соседние
  ближе 12 м - одна группа);
- группа становится контрольной точкой, если встречается минимум в 3 рейсах и разброс
  положения (MAD) не больше 0.5 м.

Используются 32 точки: по 11 на каждое направление на карте и 10 на конечных вне карты.
Большая часть - платформы: у платформы трамвай встаёт по одной и той же разметке, разброс
0.04-0.3 м. Точек больше, чем платформ, потому что в одном месте может быть несколько
устойчивых мест остановки, например стоп-линия светофора прямо у платформы.

**Как используется остановка:**
1. Трамвай стоит дольше 5 с: обе тележки показывают меньше 0.3 км/ч.
2. Берётся ближайшая к текущей оценке `s` контрольная точка `s_st`.
3. Если `|s_st − s| < max(5 м, 3σ_s)`, это она: обновление Калмана с `σ = 1 м`. Путь `s`
   сдвигается к `s_st`, неопределённость `σ_s` падает почти до 1 м, точка добавляется в
   регрессию масштаба.
4. Если дальше - остановка не используется: трамвай стоит где-то ещё.
5. Одна и та же точка повторно не используется, пока трамвай не проедет 50 м: иначе
   медленное подползание к платформе дало бы две поправки.

Проезд без остановки ничего не меняет: поправка нужна только при стоянке, потому что только
тогда известно, где именно трамвай стоит.

**Пробки и светофоры - чем отличаются от станций.** Трамвай часто стоит и в других местах: за
впереди идущим трамваем перед платформой, в пробке, у светофора. Такие стоянки тоже бывают в
одних и тех же местах, но каждый раз немного по-разному: положение зависит от длины очереди,
разброс - метры, а не сантиметры. Если принять такую стоянку за станцию в 5 метрах впереди,
оценка «прыгнет» на 5 м не туда.

Поэтому места очередей выделены отдельно: 12 мест, где стоянки вне контрольных точек (дальше
3 м от них) повторялись минимум в 2 рейсах, с разбросом `σ_q ≥ 2 м`. На каждой стоянке
сравниваются две гипотезы:
- «у станции»: `N(s_st − s; 0, σ_s² + 1)`;
- «в известном месте очереди»: `N(s_q − s; 0, σ_s² + σ_q²)`.

Если очередь правдоподобнее, привязки к станции нет, а положение слегка уточняется к месту
очереди с её большой погрешностью. Стоянки в незнакомых местах отсекаются допуском.

**Конечные.** Места стоянки на конечных (вне официальной карты) используются осторожнее:
только для поправок до 5 м, не раньше 30 м после выставки и без участия в оценке масштаба.

**Масштаб пути.** По принятым станциям строится взвешенная регрессия `s_st = b + k · odo`:
- `odo` - интеграл скорости колёс;
- ridge-априор `σ_k = 0.005` вокруг 1;
- свободный сдвиг `b` поглощает ошибку выставки;
- изменения `k` меньше 0.2 % игнорируются.

`k` умножает дальнейшее перемещение. Так систематическая разница между колёсами и длиной
карты убирается без GNSS.

## 6. Карта, выставка и два режима работы с GNSS

### 6.1. Карта

- **Координаты** - официальные осевые линии путей в MGRS 37U local: `x = UTM37N_E − 300000`,
  `y = UTM37N_N − 6100000`, `z` - уровень головки рельса. Эталон `base_link` лежит на карте с
  медианой отклонения 5 см.
- **Высота** уточнена по train: в окнах по 50 м берётся медианное расхождение высоты GNSS с
  картой, половина его прибавляется к `z` карты (`analysis/map_height.py`).
- **Конечные.** Карта покрывает двухпутный участок 4.7 км. Разворотные кольца и тупики
  достроены по GNSS train-прогонов и по публичной геометрии OSM (ODbL), совмещённой с
  train-участками (`build_osm_route.py`, `east_map.py`). Итог - 18 вариантов маршрута
  «начало + карта + конец», сцепленных с обратным направлением через кольцо.
- **Высота достроенных участков.** Высота GNSS в отдельной записи бывает сдвинута на метры.
  Поэтому у стыка с картой высота подгоняется к карте, а дальше поправка плавно убывает до нуля
  на 100 м. Без этого тупик западной конечной был бы завышен на 2.8 м.

### 6.2. Выставка (в обоих режимах)

GNSS нужен в первые секунды, чтобы найти вариант маршрута и начальное `s`.

1. Берутся фиксы RTK (`status == 2`) обеих антенн за 3 с после первого такого фикса.
2. Точка `base_link = master + 9.873 · unit(rover − master)`, `z = alt − 3` проецируется на
   все варианты маршрута, включая все проходы маршрута через одно и то же место.
3. Подходящий вариант: путь ближе 8 м, курс пути совпадает с направлением master → rover,
   направление движения по GNSS совпадает с одометром колёс. Среди равных - вариант, у
   которого больше пути впереди.
4. Если привязка ближе 15 м к началу маршрута или путь дальше 8 м, трамвай может стоять вне
   карты (например, внутри кольца). Тогда начальная неопределённость положения `σ_s = 30 м`,
   и первая станция исправит положение, а не будет отброшена.
5. Запасные варианты: ближайший путь в пределах 40 м; если GNSS нет вовсе, через 10 с
   (`gnss_wait`) берутся параметры `initial_x/_y/_yaw`.

### 6.3. Режим без GNSS по ходу рейса

Включается параметром `gnss_correction: false` или сам собой, если после выставки фиксы не
приходят. GNSS после выставки не используется совсем (с `false` узел закрывает подписки).

- **Скорость** - фильтр по колёсам и модели тяги (§4).
- **Положение** `s` - интеграл скорости вдоль выбранного варианта маршрута (§5).
- **Накопленную ошибку сбрасывают остановки:** стоянка у станции - поправка `s` к месту
  станции с точностью ~1 м; стоянка в известном месте очереди или у светофора - слабая
  поправка к этому месту; по нескольким станциям уточняется масштаб пути (§5).
- **Ветка на западной конечной** определяется по скорости. После конца карты путь расходится
  на разворотное кольцо и тупик. По положению их не отличить, а по скорости можно: в кольце
  крутая кривая и скорость не выше ~4.6 м/с, в тупик трамвай разгоняется до 5.4-7.4 м/с. По
  умолчанию выбирается кольцо. Если на участке 20-200 м после развилки скорость выше 5.0 м/с,
  оценка переходит на вариант с тупиком при той же `s` (до развилки варианты совпадают).
- **Точность:** val 1.64 м, bag чекера 1.5-1.7 м (`МЕТРИКИ.md`). Между станциями ошибка
  растёт на 0.1-0.3 % пройденного пути.

### 6.4. Режим с GNSS по ходу рейса (по умолчанию)

Всё как в §6.3, но если фиксы GNSS приходят и после выставки (организаторы это разрешили),
они мягко поправляют `s`. Подписка пассивная: узел ничего не запрашивает, а обрабатывает
фиксы, когда они есть. Скорость от GNSS не зависит.

**Какой фикс принимается.** Фикс считается шумным и проходит все проверки:

1. только RTK (`status == 2`);
2. **сверка двух антенн.** Приёмник после потери сигнала может десятки секунд выдавать фиксы
   со статусом RTK, но со сдвигом в метры. Это видно по расстоянию между антеннами: если у
   второй антенны есть фикс не дальше 0.5 с, расстояние между ними должно быть равно 12.436 м
   с допуском `0.5 м + v·dt`. Иначе фиксы не используются 10 с, а поправка, уже сделанная по
   первому фиксу этой пары, отменяется. Если фикса второй антенны рядом нет, фикс принимается
   (в bag чекера антенны присылают RTK-фиксы в разное время);
3. точка антенны переносится на ближайший путь текущего варианта маршрута - только в пределах
   ±60 м от текущей оценки, чтобы не спутать проходы маршрута через одно место, - и сдвигается
   вдоль пути на расстояние от антенны до `base_link` (master +9.873 м, rover −2.563 м);
4. точка дальше 2.5 м от пути отбрасывается (за развилкой западной конечной - 5 м: там
   несколько соседних путей тупиков, а на карте только один);
5. расхождение фикса с оценкой больше `max(15 м, 3·√(σ_s² + 3²))` - фикс отбрасывается;
6. не больше одной поправки в секунду.

**Как делается поправка** (фильтр Калмана по одной координате `s`):

```
k   = σ_s² / (σ_s² + σ_g²),   σ_g = 3 м - принятая погрешность фикса
s   ← s + k · (s_фикса − s)
σ_s² ← (1 − k) · σ_s²
```

`σ_s` - текущая неопределённость положения вдоль пути (растёт с пройденным путём, падает на
станциях). Погрешность фикса 3 м взята с запасом: один шумный фикс сдвигает оценку лишь
частично, несколько согласных - уверенно. Масштаб пути и скорость фиксы не меняют.

**Ветка на западной конечной.** Три фикса подряд после развилки, которые ближе к другой ветке
больше чем на 6 м, переключают ветку («кольцо» ↔ «тупик»). У самой развилки ветки ближе 6 м
друг к другу, и там шумный фикс ветку не решает. После такого переключения правило по скорости
(§6.3) не действует.

**Точность:** val 1.50 м при пачках GNSS по 5 с раз в 2 мин, bag чекера 1.1-1.2 м
(`МЕТРИКИ.md`).

## 7. Выходы

- `/result/velocity` - `VelocitySensor.velocity = v` (м/с), `frame_id = base_link`.
- `/result/position` - `nav_msgs/Odometry`:
  - `pose.position` - `base_link` в MGRS 37U local;
  - `orientation` - курс пути в точке `s`;
  - `twist.linear.x = v`;
  - ковариации: вдоль пути `σ_s²`, поперёк 0.3², скорость `P`;
  - `frame_id = map`, `child_frame_id = base_link`.
- `/result/diagnostics` (1 Гц): выставка, вариант маршрута, `s`, `σ_s`, флаг
  проскальзывания, число отвергнутых показаний и коррекций, масштаб, частота выхода, задержка.
- Штамп каждого выхода - штамп входного сообщения, которое его породило. Публикация идёт на
  каждое принятое входное сообщение.
