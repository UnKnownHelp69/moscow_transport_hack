# Метрики: точность и быстродействие

Критерий: методика сравнения с GNSS-эталоном, таблицы ошибок, графики, замеры задержки,
частоты и ресурсов.

Все цифры - для поставляемой версии: код и `params.yaml` этой ветки, модель в
`tram_odometry/tram_odometry/data/` (калибровка только по train и архиву OSM).

**Коротко.** Основной режим - без GNSS после выставки: колёса, контроллер и карта.

| без GNSS по ходу рейса | RMSE положения 3D | другое |
|---|---|---|
| bag чекера (независимый), ROS | 1.5-1.7 м | медиана мгновенной ошибки 0.51 м, p95 1.7 м, первые 20 мин 0.79 м |
| val, 30 рейсов (~160 км) | 1.64 / 1.27 м (среднее / медиана) | дрейф в конце 0.012 % пути (медиана) |
| train, 30 рейсов | 1.32 / 0.90 м | |

С GNSS по ходу рейса на bag чекера 1.1-1.2 м (§2а, §3). Скорость 0.046-0.049 м/с в обоих
режимах: GNSS в неё не входит.

## 1. Методика

- **Данные.** 122 прогона, из них 25 пар побайтных дубликатов, итого 97 уникальных. У 64 есть
  GNSS-эталон. Они поделены пополам:
  - **train (32)** - только калибровка: маршруты, станции, модель тяги, масштаб колёс;
  - **val (32)** - оценка.

  Из val исключены 2 прогона, где GNSS появляется только через 364 и 988 с: по условию
  проверочные прогоны дают GNSS в первые секунды. Val использовался для выбора вариантов модели,
  поэтому независимая проверка - bag чекера организаторов (§3), его нет в наших данных.
- **Воспроизведение** причинное: события идут в порядке `header.stamp`, GNSS отдаётся оценщику
  только в первые 3 с после первого валидного фикса (режим `start`; режимы с GNSS по ходу рейса -
  §2а). Ядро (`estimator.py`) то же, что в ROS-ноде.
  Тест причинности: если заменить все GNSS после окна выставки мусором, выход не меняется
  (178 648 выходов идентичны).
- **Эталон положения** - `base_link`, восстановленный из двух антенн по tf организаторов:
  `master + 9.873·unit(rover − master)`, `z = alt − 3.0`, MGRS 37U. Берутся фиксы `status == 2`,
  где master и rover отстоят не больше чем на 60 мс. Эталон скорости - `|master/vel|`.
- **Сопоставление** - ближайший штамп с допуском 0.05 с, как у чекера.
- **Метрики** считаются по прогону, затем усредняются по прогонам (среднее / медиана / худший):
  - RMSE скорости;
  - RMSE 3D-ошибки положения, её P95 и максимум;
  - ошибки вдоль и поперёк пути, по высоте;
  - дрейф в конце - ошибка в последней точке, делённая на пройденный путь.

Скрипты: `analysis/evaluate.py` (метрики), `analysis/robustness.py` (инъекция сбоев),
`analysis/plot_results.py` (график и таблица по прогонам [`results_val.csv`](results_val.csv)).

## 2а. GNSS по ходу рейса

Та же оценка, но GNSS после выставки отдаётся оценщику: пачками по 5 с каждые 2 мин (`burst`),
по одному фиксу каждой антенны раз в 30 с (`sparse`) или весь прогон (`all`). Эталон - тот же
GNSS, поэтому для `all` оценка оптимистична.
Запуск: `TRAM_EVAL_GNSS=burst python analysis/evaluate.py val`.

| режим | val: RMSE положения, среднее / медиана / худший | val: вдоль пути, среднее / медиана | train: RMSE положения, среднее / медиана / худший |
|---|---|---|---|
| только выставка (`start`), без GNSS в пути | 1.64 / 1.27 / 4.15 м | 1.25 / 0.86 м | 1.32 / 0.90 / 6.79 м |
| пачки раз в 2 мин (`burst`) | **1.50 / 1.19 / 4.08 м** | 1.07 / 0.62 м | **1.13 / 0.77 / 5.77 м** |
| по фиксу каждой антенны раз в 30 с (`sparse`) | 1.45 / 1.15 / 4.05 м | 1.00 / 0.60 м | 1.14 / 0.79 / 5.77 м |
| весь прогон (`all`) | 1.38 / 1.13 / 4.07 м | 0.91 / 0.59 м | 1.07 / 0.71 / 5.82 м |

- Скорость во всех режимах та же (val 0.046, train 0.061 м/с): GNSS в неё не входит.
- С пачками GNSS лучше больше чем на 0.05 м становятся 21 прогон val из 30 и 18 из 30 train;
  сильнее всего выигрывают прогоны, где мало остановок у станций (train `4d487b0d`: 3 станции
  за рейс, 6.79 → 3.18 м).
- Хуже без GNSS в пути не становится ни один прогон больше чем на 0.06 м, кроме val
  `0f120b35` в режиме `all` (0.58 → 0.71 м).
- Сверка антенн (`МОДЕЛЬ.md` §6а) нужна: без неё сбойные фиксы со статусом RTK портили train
  `3e9f4952` с 0.65 до 2.72 м (со сверкой 0.59 м), а ложный выбор ветки по шумному фиксу -
  val `27e994fc` (4.51 м; с порогом 6 м 2.97 м).

## 3. Проверка чекером организаторов (ROS 2, независимый bag)

Пакет `check-code`: узел `metrics`, эталон `/localization/kinematic_state`, bag
`30618_88aea4d9`, ~22 мин. Этот bag не входил ни в train, ни в val. Сборка colcon, запуск
`ros2 bag play --rate 2` и наш узел с `params.yaml`.

В bag чекера GNSS приходит всю запись, редкими пачками по 1-2 с (RTK-фиксы master и rover в
разное время), поэтому с настройками по умолчанию узел мягко поправляется по ним (`МОДЕЛЬ.md`
§6а). Для сравнения - прогон, где GNSS только для выставки (`gnss_correction:=false`). Везде
наш пакет сообщений (есть `DriverControllerCommand`).

| режим | RMSE положения 3D | max 3D | RMSE z | RMSE скорости |
|---|---|---|---|---|
| GNSS только для выставки | 1.61 м | 19.7 м | 0.19 м | 0.049 м/с |
| с GNSS по ходу рейса (по умолчанию) | **1.16 м** | 11.1 м | 0.21 м | **0.049 м/с** |

Распределение мгновенной 3D-ошибки по всем точкам bag (офлайн, эталон чекера):

| режим | RMSE | медиана | p95 | max |
|---|---|---|---|---|
| GNSS только для выставки | 1.42 м | 0.51 м | 1.72 м | 20.0 м |
| с GNSS по ходу рейса | 1.08 м | 0.53 м | 1.71 м | 11.0 м |

Медиана и p95 почти одинаковы: на большей части рейса оценка без GNSS не хуже, разница в
RMSE и максимуме - только конец рейса в тупике (ниже).

Ошибка по минутам (офлайн, тот же bag):

| | минуты 0-20 | последняя минута (тупик западной конечной) | весь bag |
|---|---|---|---|
| GNSS только для выставки | 0.79 м | 6.0 м | 1.42 м |
| с GNSS по ходу рейса | 0.79 м | 3.8 м | 1.08 м |

Весь выигрыш - на конечной: в конце записи трамвай заезжает на соседний путь тупика, которого
нет на карте (3-3.5 м от нашего тупика). По фиксам оценка переходит на ближайшую ветку и
держится у пути, а без GNSS уходит вдоль тупика.

- **Высота.** Высота тупика западной конечной была завышена на 2.8 м (`МОДЕЛЬ.md` §6), после
  исправления RMSE z 0.38 → 0.19 м.
- **Разброс между прогонами.** Время доставки сообщений в ROS каждый раз немного другое, поэтому
  RMSE положения на этом bag колеблется от прогона к прогону: 1.5-1.7 м без GNSS в пути,
  1.1-1.2 м с ним.
- **Максимум ошибки** - последние секунды рейса, в тупике западной конечной.
- **Порог развилки** 5.0 м/с выбран после этого bag (трамвай заезжал в тупик на 5.44 м/с) и
  проверен на val (1.82 → 1.78 м) и train (ложных переключений нет). Поэтому bag чекера для
  этого параметра - не независимая проверка.
- **Отставание эталона скорости.** Эталонная скорость чекера (`twist.linear.x` из
  `/localization/kinematic_state`) отстаёт от датчиков примерно на 0.09 с: если сдвинуть нашу
  скорость на 0.09 с назад, RMSE на этом bag падает с 0.049 до 0.025 м/с. Это свойство эталона,
  а не ошибка оценки: относительно GNSS-скорости (§2) наша скорость по времени совпадает с
  датчиками, и любой сдвиг только ухудшает результат (медиана val 0.029 → 0.053 м/с при
  сдвиге 0.09 с). Поэтому мы это не компенсируем и публикуем скорость на момент её штампа.

## 4. Устойчивость к сбоям (критерий 3)

Искусственные сбои на входах 16 прогонов val, эталон не трогается. «Без модели» - среднее
тележек, «с моделью» - итоговый фильтр.

| сценарий | RMSE скорости, м/с: без → с моделью | RMSE положения, м: без → с моделью |
|---|---|---|
| без сбоев | 0.053 → **0.041** | 2.02 → **1.67** |
| задняя тележка «залипла» в 0 на 30 с (×3 за рейс) | 1.050 → **0.042** | 179.2 → **1.69** |
| 1 % выбросов ±20…60 км/ч | 0.451 → **0.044** | 7.48 → **1.74** |
| 5 % NaN и отрицательного мусора | 0.054 → **0.041** | 2.03 → **1.68** |
| обе тележки молчат 3 с каждую минуту | 0.188 → **0.094** | 6.67 → **2.67** |
| пробуксовка обеих тележек +15 % на 4 с (×10) | 0.276 → 0.226 | 19.7 → 13.5 |
| юз обеих тележек −25 % на 3 с (×10) | 0.266 → 0.265 | 25.4 → 24.0 |

Отказ одной тележки, выбросы, мусор и пропуски полностью парируются.

Синхронное проскальзывание обеих тележек детектируется (флаг `slip` в диагностике), но
компенсируется лишь частично: модель тяги слишком груба, чтобы несколько секунд вести скорость
точнее колёс. На реальных данных подтверждённых эпизодов проскальзывания нет: колёса совпадают
со скоростью GNSS с RMSE 0.03 м/с. Реальная аномалия датчика есть: задняя тележка
`30639_3b3d9eb8` около 30 с показывает 0 на ходу.

## 5. Быстродействие (критерий 4)

ROS 2 Humble, `ros2 bag play --rate 1`, bag чекера `30618_88aea4d9` (~22 мин), 4-ядерная
виртуальная машина:

| показатель | значение | требование |
|---|---|---|
| частота `/result/velocity` и `/result/position` | 40 Гц (на каждое входное сообщение) | ≥ 10 Гц, рекоменд. 20-50 |
| задержка вход → публикация, среднее | 0.34 мс | ≤ 100 мс |
| задержка, максимум за прогон | 12.5 мс (99 % секундных максимумов ≤ 3.6 мс) | пик ≤ 250 мс |
| CPU ноды, среднее | 3.4 % одного ядра | ≤ 2 ядра |
| память (RSS) | 99 МБ, не растёт | ≤ 0.5 ГБ |
| ядро оценщика офлайн | 18 мкс на выход | - |

Память не растёт: история команд и окна детектора ограничены по времени, массивы маршрутов
загружаются один раз. Интернет при сборке и работе не нужен.
